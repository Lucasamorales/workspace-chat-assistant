# 0003 — Out of office: two modules, `ooo` and `leave`

Date: 2026-09-21 · Status: accepted (Robin) · Replaces: Remy's leave-automation Apps Script

## Context

Two Apps Scripts handle out-of-office today: a Sheet with a dialog that creates and cancels leave,
and a Chat bot that answers "who's out". Both are kept for reference in
`legacy/ooo-appsscript/`. The Sheet's script carries an inlined service account private key with
domain-wide delegation over the whole `calendar` scope, so anyone able to open the script can act
as any person in the domain.

Creating an OOO block **on the employee's own calendar** is the hard part: the event must auto-decline
their meetings, which only works on their own calendar, not on a shared one.

## Decision

**Two separate modules.** `ooo` answers "who's out" and only ever reads a shared calendar:
no delegation, no writes, open to the domain. `leave` books and cancels leave, and is the only
code that touches the delegation. Either can be switched off without the other.

**`leave` gets domain-wide delegation for `buddy-bot`, fenced in four ways.**

1. **No key material.** `buddy-bot` runs on Cloud Run with its own identity and mints impersonation
   tokens through the IAM Credentials API (`signJwt`, granted `roles/iam.serviceAccountTokenCreator`
   on itself). There is no key file to store, leak or rotate.
2. **`calendar.events` scope only**, not `calendar`: create and delete events, never calendar
   settings, sharing or ACLs.
3. **The impersonated user is the Chat-verified sender**, taken from the request Google signed —
   never from a form field or from anything Claude produced. Booking leave for someone else
   requires the `leave.admin` role (`BUDDY_ROLE_LEAVE_ADMIN`).
4. **Every write needs an approval click** and is logged with the requester, the subject and the
   dates.

Reads ("who's out") were meant to use no delegation at all: `ooo` would read
`accounts@example.com` through a normal share. **Amended 2026-09-22 — see below.**
`wholeteam@` is the company-wide address the `leave` module invites when it books leave; the two
modules use different addresses for different jobs.

## Amendment, 2026-09-22: `ooo` reads by acting as one account

Workspace will not let an outside address see event details on a calendar, only free/busy, and
the policy is domain-wide. Free/busy cannot answer "who is out" — it has no names. Changing the
policy for one account (a configuration group or sub-OU) was offered and was not taken, so `ooo`
reads the calendar by **acting as one fixed account** instead, using the delegation `buddy-bot`
already holds for `leave`.

This gives up the clean split where `ooo` held no impersonation power. It adds nothing to the
service account — the delegation exists either way — but it widens which code may use it, so the
fences are in the code, not only in configuration:

- **The account acted as comes from `OOO_READ_AS` in settings**, validated as one ordinary address.
  Nothing a user, a message or Claude produces can reach it; the `who_is_out` tool takes a period
  and nothing else.
- **The read-only scope is requested first** (`calendar.events.readonly`). The writable
  `calendar.events` is used only while the delegation lacks the read-only scope, and every fallback
  is logged with the fix. Adding that scope to the delegation entry removes the write power entirely.
- **The reader cannot write.** `createOooCalendar` returns a frozen object with `list` and
  `describe` — no create, delete or patch exists; requests are built inside the module, always GET,
  always the configured calendar, and a caller cannot supply a method, body or URL.
- **Every impersonated read is logged** with the account acted as.

Unset `OOO_READ_AS` the day the calendar can be shared with `buddy-bot` directly: the module then
falls back to its own access and holds no delegation again.

## Alternatives considered

- **Per-user OAuth**, like Asana: smaller blast radius, no delegation, but a connect step for every
  person and another token store. Rejected as too much friction for booking a day off.
- **Team calendar only**, each person adding their own OOO block: safest, but loses auto-decline,
  which is the main reason the current script exists.

## Consequences

- Delegation is domain-wide by nature: the guardrails above are code and configuration, so the
  `leave` module's tool layer is security-critical and changes to it need review.
- A Workspace admin must add the delegation, and it is visible in the Admin console alongside
  Remy's `leave-bot` entry, which should be removed once this replaces it.
- Access is split by module: `BUDDY_ACCESS_OOO` for the domain, `BUDDY_ACCESS_LEAVE` for the pilot
  (the accounts team later), with `BUDDY_ROLE_LEAVE_ADMIN` to book on someone else's behalf.
  `ooo` being open to everyone does **not** let anyone write: all it can trigger is a list of
  events on the one configured calendar.
